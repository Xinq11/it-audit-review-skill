# 接口定义、总体与成功口径

本文件用于先弄清“传什么、从哪里到哪里、何时算完成”。以下为 `R` 复核实施建议；公开背景原则见 [来源与适用性](sources.md)，具体要求以项目适用准则、方法论和接口实际设计为准，不将某种技术方案设为所有接口的必备控制。意见分为记录问题、证据不足、疑似控制例外、需要专业判断；是否构成缺陷及其等级由审计人员评价。

## IFC-001｜接口范围与控制边界

- **适用条件：** 识别接口或评价底稿范围时使用，包括批量文件、API、消息或数据库交换等实际模式。
- **所需证据：** 接口清单、数据流或接口说明、控制描述、运行周期、环境及责任分工；涉及中转或外部服务时取得相关边界说明。
- **检查动作：** 对齐源系统、目标系统、接口及版本标识、方向、业务对象、传输模式和频率。双向接口分别识别各方向及回执；明确谁监控、谁处理、谁复核，测试是否覆盖所述生产对象和目标期间。
- **例外与判断边界：** 一个名称可能包含多个作业或方向，不能凭名称相同认定范围相同；不因没有独立中间件、实时处理或单独岗位而认定问题。说明不清先确认边界，不扩展成系统总体审计。
- **意见类型：** 标识或描述不一致为 `documentation_issue`；关键范围无法确认用 `evidence_gap`；适用边界争议用 `professional_judgment`。

## IFC-002｜总体、样本及提取口径

- **适用条件：** 使用接口运行清单、业务记录或异常清单选样、核对及支持期间结论时。
- **所需证据：** 总体来源、查询或筛选条件、提取时间、期间、记录状态、加工说明、完整准确性核对及抽样依据。
- **检查动作：** 区分批次、消息、业务单据及行项目等单位；核对样本确属对应总体。检查失败、拒收、重传是否按测试目标纳入，而非仅用成功清单支持全部运行结论；追溯手工筛选、合并及删除步骤。
- **例外与判断边界：** 测试、取消或其他渠道记录可按明确规则排除，需保留理由；空表不能自动证明零发生。总体不可靠时不能只增加样本补救。样本量、选择方法及可外推范围按项目依据确认，不自行设数。
- **意见类型：** 缺提取或选样支持用 `evidence_gap`；编号、范围记录矛盾用 `documentation_issue`；外推依据需决定时用 `professional_judgment`。

## IFC-003｜生命周期与成功层次

- **适用条件：** 底稿使用成功率、完成状态、确认回执或“传输成功”支持控制结论时。
- **所需证据：** 状态字典、处理阶段说明、批次与业务标识、回执及目标业务结果；部分成功需有明细和汇总关系。
- **检查动作：** 按实际设计区分发送、接收、格式校验、业务校验、写入与业务完成，明确所测控制要求达到哪一层。核对状态变化、最终状态及对应业务对象；关注批次成功是否仍包含被拒或未完成记录。
- **例外与判断边界：** API 成功响应、队列接收或文件到达不当然表示业务已完成；也不能要求不涉及记账的接口取得入账证据。异步确认、延迟完成或允许部分成功须依设计评价，状态语义未知时不猜测。
- **意见类型：** 成功定义不清用 `documentation_issue`；缺目标结果用 `evidence_gap`；已有事实偏离明确完成要求时用 `potential_control_exception`。
